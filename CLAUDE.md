# Claude Rules — Odyssey Task 1

## 1. Explain Before Acting

Before writing, editing, or deleting any file, always:
- State **what** you are about to do (which file, which change)
- State **why** it is necessary (the reasoning, the tradeoff)
- Wait for the user to confirm before proceeding

For multi-step tasks, show the full plan first. Do not start implementation until the user agrees.

Example format:
> **What:** Add `createWebRtcTransport` handler in `server/src/room.ts`
> **Why:** mediasoup-client needs ICE/DTLS params before it can open a send transport

---

## 2. Never Commit Without Review

- **Never** run `git add`, `git commit`, or `git push` without explicit user instruction
- Before staging anything, show a `git diff` summary and ask for approval
- When the user asks to commit, present the exact commit message for review first
- Never use `--no-verify`, `--force`, or `--amend` unless the user explicitly asks

## 3. Project Standards

### Repository Layout
```
odyssey-task-1/
├── docs/               # Project documentation
│   ├── ASSIGNMENT.md
│   └── TASKS.md
├── server/             # Node.js + mediasoup + Socket.io
│   ├── src/
│   │   ├── index.ts        # Entry point — HTTP server + Socket.io init
│   │   ├── room.ts         # Room state, participant management
│   │   ├── mediasoup.ts    # Worker, Router, Transport, Producer, Consumer
│   │   └── types.ts        # Shared TypeScript interfaces
│   ├── package.json
│   ├── tsconfig.json
│   └── .env.example
└── client/             # React + TypeScript + Vite
    ├── src/
    │   ├── main.tsx
    │   ├── App.tsx
    │   ├── components/     # UI components (ArenaMap, Controls, VideoTiles)
    │   ├── hooks/          # Custom hooks (useSocket, useMediasoup, useSpatialAudio)
    │   ├── lib/            # Pure utility functions (audio, geometry, mediasoup setup)
    │   └── types.ts        # Shared TypeScript interfaces
    ├── package.json
    ├── tsconfig.json
    └── .env.local.example
```

### TypeScript
- Strict mode on (`"strict": true` in tsconfig)
- No `any` — use `unknown` and narrow, or define a proper type
- All Socket.io events typed via a shared `Events` interface on both server and client
- Prefer `type` over `interface` for plain data shapes; use `interface` for extensible contracts

### Naming
| Thing | Convention | Example |
|---|---|---|
| Files | kebab-case | `arena-map.tsx`, `use-spatial-audio.ts` |
| Components | PascalCase | `ArenaMap`, `VideoTile` |
| Hooks | camelCase with `use` prefix | `useSocket`, `useMediasoup` |
| Functions | camelCase | `calculateGain`, `clampToCircle` |
| Constants | UPPER_SNAKE_CASE | `HEARING_RADIUS`, `STEP_SIZE` |
| Socket events | kebab-case strings | `"join-room"`, `"move"`, `"mic-status"` |

### React Components
- One component per file
- Props type defined directly above the component as `type Props = { ... }`
- No default exports for utility/hook files; default export only for components
- Keep components presentational where possible — logic lives in hooks or `lib/`

### State Management
- Local UI state: `useState`
- Side-effects and subscriptions: `useEffect` with proper cleanup
- Shared socket/mediasoup state: context or a dedicated hook passed down as props
- No external state library unless complexity clearly demands it

### Styling — Tailwind CSS + shadcn/ui

**Tailwind CSS** is the only styling mechanism. No CSS Modules, no plain CSS files, no CSS custom properties.

- All layout, spacing, color, and typography via Tailwind utility classes
- Dynamic values (e.g. dot `cx`/`cy` on the SVG arena) passed as inline `style` props — keep them minimal
- Tailwind config (`tailwind.config.ts`) is the single source of truth for design tokens (colors, radii, breakpoints)

**shadcn/ui** provides base components — installed into `src/components/ui/`.

- Use shadcn components for: `Button`, `Input`, `Card`, `Badge`, `Toggle`, `Tooltip`, `Separator`
- Add new shadcn components with `npx shadcn@latest add <component>` — never hand-roll what shadcn already covers
- Extend shadcn components with `className` prop using `cn()` (from `lib/utils.ts`) — never edit files inside `src/components/ui/` directly
- Custom app components (ArenaMap, VideoTile, Controls) live in `src/components/` and compose shadcn primitives + Tailwind classes

**`cn()` utility** (auto-generated by shadcn init — `clsx` + `tailwind-merge`):
```ts
import { cn } from '@/lib/utils'
<Button className={cn('w-full', isActive && 'bg-green-500')} />
```

### Server Patterns
- Each room is isolated: one mediasoup Router per room
- All room mutation goes through a `RoomManager` class/module — no direct Map access elsewhere
- Socket event handlers are thin: validate input, delegate to `RoomManager`, emit result
- Environment config read once at startup via `dotenv`; never read `process.env` mid-request

### Error Handling
- Validate at boundaries only: socket event payloads, HTTP query params
- Use `try/catch` around mediasoup async calls and log errors with context
- Never swallow errors silently

### Comments
- No comments explaining what the code does — names must do that
- Comments only for non-obvious constraints or workarounds, e.g.:
  ```ts
  // mediasoup requires DTLS role "auto" when behind a NAT
  ```

### Git Commit Style
```
<type>: <short imperative summary>

Types: feat | fix | chore | refactor | docs | test
Max 72 chars on first line
```
Example: `feat: add distance-based gain calculation for spatial audio`
